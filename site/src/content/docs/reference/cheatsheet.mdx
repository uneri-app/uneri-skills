## The order

```text
(steering) ─▶ udd-init ─▶ udd-add ─▶ udd-validate ─▶ (udd-arrange)

then, one use case at a time:

sdd-init ─▶ sdd-requirements ─▶ sdd-clarify ─▶ sdd-design ─▶ sdd-validate-design
        ─▶ (sdd-validate-gap: existing code only) ─▶ sdd-tasks ─▶ sdd-impl
        ─▶ sdd-validate-impl ─▶ pr-upsert

sdd-compact tidies one spec whose history or drift has built up; sdd-trace audits use cases, specs and tasks across the project. Both can run at any time.
```

- `steering` is optional, and recommended for a multi-context project. Write one use case, validate, repeat.
- `review`, `debug` and `verify-completion` are called by `sdd-impl` for each task; you can also run them alone.
- `issue-upsert` and `pr-upsert` can run at any point, from a use case or an implementation branch.

## Gates

Move on only when the gate says GO.

| Gate | When | What it checks |
| --- | --- | --- |
| `sdd-validate-design` | Before `sdd-tasks` and `sdd-impl` | The quality of `design.md` |
| `sdd-validate-gap` | After the design, before `sdd-tasks` (existing code only) | The gap between the design and the codebase |
| `sdd-validate-impl` | After all tasks are implemented | The feature as a whole: GO / NO-GO |

`sdd-impl` will not start until requirements, design and tasks are approved.
