# Use Cases (<Project>)

Use cases are steering knowledge (stable across specs). Principle: `1 UC = 1 spec`.
A UC is the seed of one spec; granularity is fixed at **user-goal level (one actor
achieves one goal in one sitting) × one spec**. Upstream Domain Events / Aggregates are
defined in `domain-model.md`; each UC references them via `realizes` / `aggregates`.

## UC-ID conventions

- Format `UC-<CTX>-NNN` (`<CTX>` = bounded-context code; `NNN` = 3-digit zero-padded sequence
  **per context**).
- Number bands: **001–099 functional UCs** (user-facing) / **100– operational UCs**
  (developer-facing: CI/CD, dev environment, monitoring, …).
- **UCs are functional goals only** — non-functional requirements (performance, security,
  availability, i18n, …) are NOT UCs: cross-cutting NFRs go to steering, per-UC NFRs into the
  spec's `requirements.md`.
- IDs are immutable and never reused. Retired UCs keep their number (gaps are not refilled).
- Order: by number until the list grows; then arrange it by the user's journey with `<!-- journey: <stage> -->`
  markers (`/uneri-skills:udd-arrange`). The order never changes an ID.
- Required field: `actor` (validated against `actors.md`).
  Optional: `realizes: [EVT-…]` / `aggregates: [AGG-…]` / pre/postconditions.
  Read-model (query) UCs produce no new facts: `aggregates` only, no `realizes`.
- Do NOT write Status / Spec / Issue columns — downstream state is generated by tooling;
  this file holds upstream declarations only (no double bookkeeping).
